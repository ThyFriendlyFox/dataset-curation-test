````text
Mutation analysis is the gold standard for evaluating the quality of software test suites, and it is one of the very few techniques that can evaluate the quality of the oracles in test suites. But mutation analysis is also one of the most costly methods for evaluating test suites. The problem is that traditional mutation analysis needs to generate each syntactic variant (mutant) and evaluate it independently with the test suite. So at worst, one needs to run the whole test suite as many times as there are mutants. This can be reduced somewhat by running each test case only on the mutants whose mutation site the test case covers. But this still leaves many mutants to evaluate independently. For example, Fig. 1 has four possible mutations: m_{1} in Line 4, m_{2} and m_{3} in Line 7 and m_{4} in Line 14. Traditional mutation analysis (Fig. 2(a)) would need five executions for this, the execution of the original to find the coverage of the test suite, and four for the four mutants.

Many previous researchers have noticed that traditional mutation analysis is very redundant, and that a lot of execution cost can be saved if some of these redundancies are eliminated. Researchers have worked on eliminating these redundancies to make mutation analysis more efficient. Just and Fraser showed that not all mutants need to be executed independently. Some mutants give the same value, and so the same infected state, and only some of these are propagated. So the states resulting from mutations can be partitioned, and only the ones that result in unique propagated states need to be evaluated independently. For example, in Fig. 1, when INPUT=1, executing m_{1} gives the same state as the original. So the partitioned state execution (Fig. 2(b)) skips executing M_{1}.

In split-stream execution, a mutant is forked at runtime when the mutation is executed, and it shares the execution path up to the execution of the mutation. For example, if we execute the program (Fig. 1) with INPUT=1, a new process is spawned at each mutation. At the end this gives four new processes in total (Fig. 2(c)), but the initial execution up to the mutation is shared with the original.

The equivalence-modulo state approach is the latest of these techniques, and it combines the advantages of state-partitioning and of split-stream execution. The idea is to fork only if the mutation leads to a new unique state. This is even more efficient, since it skips M_{1} and shares the execution path between the original and the mutants and also between mutants (Fig. 2(d)).

So the current state of the art is very efficient at eliminating the causes of redundant execution up to the point where mutations cause a divergence in state. But the pre-divergence execution is not the biggest cause of redundant execution. There is no solution yet for avoiding redundant execution after the divergence, when a forked execution restarts after the execution of the original. For example, the modulo-state execution (Fig. 2(d)) forks a new mutant process from the original after executing Line 7, and this mutant process forks again in the second loop when M_{3} and M_{4} diverge. But in each of these processes the function process(i) is called with exactly the same arguments, because i is never mutated in these mutants.

In this paper we propose mutation analysis with execution taints, as a way to get much lower redundancy than the methods known before. Our proposal is based on three observations:

The first observation is that many mutants do not change the control-flow compared to the original. For example, in Fig. 1, Line 7 is mutated in mutants M2 and M3, which gives different values for a. The value of a is different in the original and in the mutants, but a never influences the control-flow, so the actual execution flow of the original and of the mutant is exactly the same. So apart from the values affected by the mutation, the other execution steps are the same. If these common execution steps can be shared between the mutants and the original program, the cost of mutation analysis goes down.

The second observation is that for mutations that do not change control flow, we can consider the mutation to introduce a unique taint in the computation, and this taint can be propagated dynamically to any values that use the results of the computation, with standard taint propagation through dynamic data-flow. These taints can be propagated with standard techniques in most languages, even if the language runtime has no direct support for taint propagation. We do not just propagate a taint flag. As long as the control-flow does not diverge, we propagate the results of computations involving mutations in the same taint. We call these taints value taints of the corresponding values. The computations involving these value taints are called execution taints of the main computation.

The third observation is that even if the control-flow diverges, the impact of the diverged control-flow can be limited to the function that contains the mutation, by merging back the execution and using memoization judiciously.

With these three observations, our technique (Fig. 2(e)) can do very efficient mutation analysis and limit both pre and post mutation redundancies.

## Contributions

- We propose a complete framework for avoiding redundancy in mutant execution, covering both the pre-divergence and the post-divergence stages.

- Our execution taints are a lightweight mechanism that repurposes dynamic data-flow taints for mutation analysis.

- We propose a novel memoization strategy to share computational results across mutants.

- We propose a comprehensive solution to the problem of mutants sharing single-use resources during forking.
````

````text
Mutation analysis is the gold standard for evaluating the quality of software test suites. It is one of the very few techniques that can actually evaluate the quality of the oracles provided by test suites. Unfortunately, mutation analysis is also one of the most costly methods for test suite evaluation. The problem is that traditional mutation analysis requires the generation and independent evaluation of each syntactic variant (mutant) by the test suite [1], which means that at worst one needs to execute the entire test suite as many times as there are mutants. This can be reduced to some extent by running each test case only on those mutants whose mutation site is covered by the test case [2]. However, this still leaves a large number of mutants to evaluate independently. For example, Fig. 1 includes four possible mutations: m_{1} in Line 4, m_{2} and m_{3} in Line 7 and m_{4} in Line 14. With traditional mutation analysis (Fig. 2(a)), this would require five executions: the execution of the original to determine the coverage of the test suite, and one for each of the four mutants.

Numerous researchers have noticed that traditional mutation analysis is highly redundant, and that significant execution cost savings can be achieved by eliminating some of these redundancies, and they have focused on doing so to make mutation analysis more efficient. Just and Fraser [3] showed that not all mutants need to be executed independently. Some mutants result in the same value, and hence the same infected state, and only some of these are propagated. Hence, one can partition the states resulting from mutations, and only those resulting in unique propagated states need to be evaluated independently. For example, in Fig. 1, when INPUT=1, the execution of m_{1} results in the same state as the original, so the partitioned state execution (Fig. 2(b)) skips the execution of M_{1}.

In split-stream execution [4,5,6], a mutant is forked when the mutation is executed at runtime, sharing the execution path until the execution of the mutation. For example, when one executes the program (Fig. 1) with, say, INPUT=1, a new process is spawned at each mutation. This results in a total of four new processes at the end (Fig. 2(c)), but with the initial execution until the mutation shared with the original.

The equivalence-modulo state approach [7] is the latest such technique, combining the advantages of state-partitioning and split-stream executions. The idea is to fork only if the mutation leads to a new unique state. This technique is even more efficient, skipping M_{1} and sharing the execution path between the original and the mutants, and also among mutants (Fig. 2(d)).

That is, the current state of the art [7] is very efficient at eliminating the causes of redundant execution up to the point where mutations cause a divergence in state. However, pre-divergence execution is not the biggest cause of redundancy. There is as yet no solution for avoiding redundant execution in the post-divergence phase, when a forked execution restarts following the execution of the original. For example, the modulo-state execution (Fig. 2(d)) forks a new mutant process from the original after executing Line 7, and this mutant process forks again in the second loop when M_{3} and M_{4} diverge. However, in each of these processes, the function process(i) is called with exactly the same arguments, because i is never mutated in these mutants.

In this paper, we propose mutation analysis with execution taints as a way to achieve much lower redundancy than previously known methods. Our proposal is based on three observations:

The first observation is that many mutants do not change the control-flow from the original. For example, in Fig. 1, Line 7 is mutated in mutants M2 and M3, resulting in different values for a. Even though the value of a differs between the original and the mutants, a never influences the control-flow, so the actual execution flow of the original and the mutant is exactly the same. That is, except for the values affected by the mutation, the other execution steps are the same. Hence, the cost of mutation analysis can be reduced if such common execution steps are shared between these mutants and the original program.

Our second observation is that for mutations that do not change control flow, one can consider the mutation to have introduced a unique taint in the computation, and this taint can be propagated dynamically to any values using the results of the computation, through standard taint propagation via dynamic data-flow. Such taints can be propagated using standard techniques in most languages, even if the language runtime has no direct support for taint propagation [11,12]. We do not simply propagate a taint flag: as long as there is no control-flow divergence, we propagate the results of computations involving mutations in the same taint. We call such taints the value taints of the corresponding values, and the computations involving such value taints the execution taints of the main computation.

Our third observation is that even when the control-flow diverges, it is possible to limit the impact of the diverged control-flow to the function containing the mutation, using merge-back of execution and judicious memoization.

Using these three observations, our technique (Fig. 2(e)) can perform extremely efficient mutation analysis, limiting both pre and post mutation redundancies.

## Contributions

- • We propose a complete framework for avoiding redundancy in mutant execution, covering both the pre-divergence and post-divergence stages.

- • Our execution taints are a lightweight mechanism that repurposes dynamic data-flow taints for mutation analysis.

- • We propose a novel memoization strategy for sharing computational results across mutants.

- • We propose a comprehensive solution to the problem of mutants sharing single-use resources during forking.
````

````text
Mutation analysis is the gold standard for evaluating the quality of software test suites. It is one of the very few techniques that can actually evaluate the quality of oracles provided by software test suites. Unfortunately, mutation analysis is also one of the most costly methods for test suite evaluation. The problem is that traditional mutation analysis requires generation and independent evaluation of each syntactic variant (mutant) by the test suite [1]. This means that one needs to execute the entire test suite as many times as the number of mutants at worst. This can be reduced to some extent by running each test case only on those mutants whose mutation site is covered by the test case [2]. However, this still leaves a large number of mutants to evaluate independently. For example, Fig. 1 includes four possible mutations: m_{1} in Line 4, m_{2} and m_{3} in Line 7 and m_{4} in Line 14. With traditional mutation analysis (Fig. 2(a)), this would require five executions including the execution of original to determine coverage of the test suite, and four from each of the four mutants.

Numerous previous researchers have noticed that traditional mutation analysis is highly redundant, and significant execution cost savings can be achieved if one can eliminate some of these redundancies. Researchers have focused on eliminating these redundancies to make mutation analysis more efficient. Just and Fraser [3] showed that not all the mutants need to be executed independently. Some mutants result in the same value, and hence the same infected state, and only some of these are propagated. Hence, one can partition states resulting from mutations, and only those resulting in unique propagated states need to be evaluated independently. For example, in Fig. 1, when INPUT=1, execution of m_{1} results in the same state as the original. Hence, the partitioned state execution (Fig. 2(b)) skips the execution of M_{1}.

In split-stream execution [4,5,6], a mutant is forked when the mutation is executed at runtime, which shares the execution path until the execution of the mutation. For example, when one executes the program (Fig. 1) with say INPUT=1, at each mutation, a new process is spawned. This results in a total of four new processes at the end (Fig. 2(c)), but with the initial execution until the mutation shared with the original.

The equivalence-modulo state approach [7] is the latest such technique, and it combines the advantages of state-partitioning and split-stream executions. The idea is to fork only if the mutation leads to a new unique state. This technique is even more efficient, skipping M_{1} and sharing the execution path between original and also between mutants (Fig. 2(d)).

That is, the current state of the art [7] is very efficient in eliminating the causes of redundant execution until the point where mutations cause a divergence in state. However, the biggest cause of redundancy of execution is not the pre-divergence execution. There is no solution yet for avoiding redundant execution in the post-divergence execution phase when a forked execution restarts following the execution of the original. For example, the modulo-state execution (Fig. 2(d)) forks a new mutant process from the original after executing Line 7 and this mutant process forks again in the second loop when M_{3} and M_{4} diverge. However, in each of these processes, the function process(i) is called with exactly the same arguments because i is never mutated in these mutants.

In this paper, we propose mutation analysis with execution taints as a way to achieve much lower redundancy than previously known methods. Our proposal is based on three observations:

The first observation is that many mutants do not produce a change in the control-flow from the original. For example, in Fig. 1, the line Line 7 is mutated in mutants M2 and M3 resulting in different values for a. Even though the value of a is different in the original and mutants, since a never influences the control-flow, the actual execution flow of the original and the mutant is exactly the same. That is, except for the values affected by the mutation, the other steps of execution are the same. Hence, one can reduce the cost of mutation analysis if such common execution steps can be shared between such mutants and the original program.

Our second observation is that for such mutations that does not change control flow, one can consider the mutation to have introduced a unique taint in the computation, and this taint can be propagated dynamically to any values using the results of the computation using standard taint propagation through dynamic data-flow. Such taints can be propagated using standard techniques in most languages even if the language runtime does not have direct support for taint propagation [11,12]. We do not simply propagate a taint flag. As long as there is no control-flow divergence, we propagate the results of computations involving mutations in the same taint. We call such taints value taints of corresponding values. The computations involving such value taints are called execution taints of the main computation.

Our third observation is that even when there is a control-flow divergence, it is possible to limit the impact of diverged control-flow to the function containing the mutation using merge-back of execution and judicious use of memoization.

Using these three observations, our technique (Fig. 2(e)) can perform extremely efficient mutation analysis limiting both pre and post mutation redundancies.

## Contributions

- • We propose a complete framework for avoiding redundancy in mutant execution including both pre-divergence and post-divergence stages.

- • Our execution taints is a lightweight mechanism that repurposes dynamic data-flow taints for mutation analysis.

- • We propose a novel memoization strategy for sharing computational results across mutants.

- • We propose a comprehensive solution to the problem of sharing single-use resources by mutants during forking.
````
